The protocol

What is MCP?

Model Context Protocol — standardized AI tool calling

Tools

Functions your server exposes. The AI decides when to call them. You define the name, description, and typed parameters.

Protocol messages

initialize → handshake · tools/list → discovery · tools/call → execution

Transport: stdio vs HTTP

stdio — local subprocess   Streamable HTTP — cloud deployment ✓

from fastmcp import FastMCP

mcp = FastMCP("idea-vault")

@mcp.tool()
def save_idea(
    content: str,
    tags: list[str] = [],
) -> dict:
    """
    Save an idea to the vault.
    This docstring is what the AI reads
    to decide when to call this tool.
    """
    id_ = generate_id()
    ideas[id_] = {"content": content, "tags": tags}
    return {"saved": True, "id": id_}
FastMCP auto-generates JSON Schema from type hints.
Your docstring = the AI's understanding of the tool.
The architecture decision

Why YOUR own MCP server?

Existing servers (Notion, GitHub) don't cover personal context

1. Private personal data

Your idea pool, decision history, style library. Doesn't live in any SaaS. Lives in your server.

2. Domain-specific reasoning

Not just CRUD on existing data. Your server knows how your data is organized and what queries make sense.

3. Cross-tool sharing

Same vault accessible from Antigravity AND Gemini CLI. One server, every client. The M+N value made real.

4. Composition

Your server can call multiple SaaS APIs and return one combined result. A personal integration hub.

Existing MCP servers wrap shared organizational data. You need your own for private personal context.
The context layer

"Can't I just tell the AI to remember?"

AI clients are stateless. MCP is the persistence layer.

Stateless. Every new conversation = zero memory. Yesterday's ideas are gone.
Context-window limited. Stuffing ideas into the prompt runs out at ~200K tokens.
General purpose. No awareness of your taxonomy, tags, or idea categories.
MCP addresses all three:
✓ Persistent — ideas survive conversation boundaries
✓ Queryable — find_ideas("python") fetches only relevant ideas
✓ Structured — typed fields, tags, timestamps, IDs
✓ Scalable — 10K ideas, same query speed
✓ Multi-client — Antigravity + Gemini CLI share one vault
MCP is the personal-context layer that makes a generic AI feel like it knows you.

The critical flag

Cloud Run + in-memory state

One flag that must never be forgotten

Without --max-instances=1

Cloud Run auto-scales under load → 2 instances → 2 separate Python processes → 2 separate dicts in RAM.

Instance A saves idea. Instance B handles find. B's dict is empty. Ideas vanish randomly. Maddening to debug.
With --max-instances=1

One process. One dict. Consistent state. Saved = findable. 
# Required deploy command
gcloud run deploy idea-vault \
  --source . \
  --region us-central1 \
  --allow-unauthenticated \
  --max-instances 1 \
  --port 8080
This is a constraint, not a solution.
Max-instances=1 → no horizontal scaling.
Fine for a personal vault. Not for production.
→ Week 5: database storage removes this constraint.
Stretch goal

CI/CD: pain motivates solution

The best way to understand automation is to suffer without it

The journey every engineer takes:
1st deploy: "cool, that worked"
2nd deploy: "fine"
3rd deploy: "I keep forgetting those flags…"
4th deploy: "why 3 minutes every single time?"
5th deploy: "there has to be a better way"
That frustration is the correct motivation. Not "best practices."
name: Deploy to Cloud Run
on:
  push:
    branches: [main]

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: google-github-actions/auth@v2
        with:
          workload_identity_provider: ${{ secrets.WIF_PROVIDER }}
          service_account: ${{ secrets.WIF_SERVICE_ACCOUNT }}
      - run: |
          gcloud run deploy idea-vault \
            --source . \
            --region us-central1 \
            --allow-unauthenticated \
            --max-instances 1 \
            --port 8080

Push to main → auto-deploys. The friction is gone.

What you just saw

Demo recap

Doctrine applied in 5 moves

1
spec.md first. Out-of-scope list written before any code. "No LLM calls inside MCP tools." This rule got tested in step 4.
2
Context-loaded generation. spec.md + mcp-quickref.md in context → correct FastMCP syntax on the first try.
3
Deployed with --max-instances=1. One flag, consistent in-memory state. Forget this flag and ideas vanish randomly.
4
Drift refusal. AI suggested summarize_all_ideas with an internal Gemini call. spec.md said "data tools only." We said no.
5
Admin as Critic. Opened /admin/ideas and confirmed the AI was saving real ideas — not chat snippets.
