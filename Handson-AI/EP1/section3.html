The Scaling Challenge

What "1,000 runners" actually means
  • 1,000 independent ADK sessions — each with its own state
  • Each runner: receives tick → process_tick → writes to Redis
  • All 1,000 must complete before clock advances
  • Cloud Run: stateless, session state must be external
Why this is hard
  • Session reads/writes every tick → latency compounds
  • 1,000 WebSocket frames → thundering herd
  • Agent communication → N×M fan-out if not batched

Bottleneck #1 — Session Storage

Session storeVerdictWhy
SQLite (ADK default)❌File locking thrashes under concurrent agents
InMemorySessionService❌No cross-process sharing
VertexAiSessionService❌~200 ms/call round-trip
AlloyDB / PostgreSQL❌Connection overhead + row locking
Redis (Memorystore)✅Sub-millisecond, shared across processes
The fix: PrunedRedisSessionService

Wraps community RedisSessionService with event pruning — without pruning, session blob grows ~4 events/tick → progressive degradation at 1,000 runners.

Bottleneck #2 — Agent Communication

HTTP is too slow for 1,000 tick-synchronized agents

Gateway ── publish ──▶
simulation:broadcast
runner:1
runner:2
runner:N
  • Runners hold a long-lived Redis subscription
  • Pulse arrives with sub-millisecond latency simultaneously
  • Gateway still sends HTTP poke as cold-start fallback
  • Dispatcher de-duplicates inside each runner process

Dual-poke design: Redis gives speed to warm instances. HTTP gives correctness to cold-start ones. You get both.
