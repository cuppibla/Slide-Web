When does an agent need a tool?

Not everything needs a tool. Most things don't. Here's how you tell the difference.

Instruction is enough when…

  • LLM handles it reliably (draft, summarize, translate)
  • Free text output is acceptable
  • No need to unit test the logic
  • No external / curated data needed

Tool is necessary when…

  • LLM is unreliable for this task
  • Structured data is required back
  • The function must be independently testable
  • You need to access curated / external data

The question isn't "can the LLM do this?" — it's "can the LLM do this reliably, every time?"

3 Criteria

The 3 "tool necessary" criteria

A tool earns its existence when at least one of these is true.

1
LLM is unreliable
Counting, summing, rule-checking, set operations. Works in testing, breaks in production.
mathcounting
2
Structured data needed
Downstream code needs a typed dict. "Looks balanced" is not a contract you can parse.
typed return
3
Must be testable
If it lives in an instruction, you can't write a unit test. Pure functions have tests. Instructions have vibes.
unit test

analyze_balance satisfies all three.  ·  propose_alternatives adds a fourth: access to a curated catalog the LLM doesn't have.

What makes a "good tool"?

Four properties every FunctionTool should have.

🔒
Pure function
No LLM calls inside. Deterministic input → output. If your tool calls a model, you built a mini-agent, not a tool.
📦
Typed return
Return a typed dict with known keys. The LLM and your test suite both depend on this contract. Free text isn't a contract.
🧪
Independently testable
3-line unit test. No agent. No model. No network. If you can't test it in isolation, it's not a good tool.
⚠️
LLM can't do this reliably
If a well-written instruction would work 99% of the time, skip the tool. Build tools for the 1% failures that matter in production.
Context

Docstrings are prompts

ADK reads your docstring to build the tool schema. The LLM reads the schema to decide when and how to call your tool.

✗ Bad — LLM won't know when to call it 
def analyze_balance(routine: dict) -> dict:
    """Analyzes routine balance."""
    ...

LLM sees: "analyzes balance." When? What balance? What does it return? Unknown → tool ignored.

✓ Good — LLM knows exactly when + how 
def analyze_balance(routine: dict) -> dict:
    """
    Analyzes a routine for timing accuracy
    and theme diversity.

    ALWAYS call after generating a routine,
    before presenting it to the user.

    Args:
        routine: dict with "days" key. Each day
          has "activities" list with name,
          duration_min, and theme.

    Returns:
        dict: total_minutes, minutes_per_day,
        theme_counts, theme_diversity_score,
        warnings (list[str]).

    If warnings non-empty, state each one
    and offer to fix the affected days.
    """

Rule of thumb: write the docstring for a smart colleague who needs to know when to call this, what to pass, and what comes back. That colleague is the LLM.

FunctionTool in ADK

Define a Python function, pass it to the agent — ADK does the rest.

Define the function

def analyze_balance(routine: dict) -> dict:
    """[full docstring — LLM reads this]"""
    # pure Python logic here
    # NO: model.generate(...)
    # NO: from google.adk import ...
    warnings = []
    totals = [
        sum(a["duration_min"]
            for a in day["activities"])
        for day in routine["days"]
    ]
    return {
        "total_minutes": sum(totals),
        "minutes_per_day": totals,
        "warnings": warnings,
    }

Why it's a critic

It independently checks the generator's output against rules the generator wrote. Generator creates. Critic audits. No LLM can reliably check its own arithmetic — that's exactly why the external function exists.

Why it works as a tool

Separation is the point. The critic has no stake in the output it checks. A pure function with a typed return is auditable, testable, and wrong in the same way every time — not randomly wrong.

In Weeks 5–7 we automate this: Generator → Critic → Generator loop, fully wired. Today you're building the Critic by hand.

Optional: callbacks

Observe, log, or intercept — without changing any agent logic.

before_model_callback

from google.adk.agents.callback_context \
    import CallbackContext
from google.adk.models.llm_request \
    import LlmRequest
from google.adk.models.llm_response \
    import LlmResponse
from typing import Optional
import datetime

def log_model_call(
    callback_context: CallbackContext,
    llm_request: LlmRequest,
) -> Optional[LlmResponse]:
    ts = datetime.datetime.now().strftime(
        "%H:%M:%S")
    print(f"[{ts}] === MODEL CALL ===")
    return None  # None = proceed normally
agent = Agent(
    ...,
    before_model_callback=log_model_call
)

When callbacks are useful

  • Observability — log every LLM call
  • Debugging — see what the model receives
  • Caching — return LlmResponse to skip the call
  • Rate limiting — intercept and delay

analyze_balance — the critic function

Pure Python. No LLM. Deterministic. Testable. This is what a good tool looks like.

def analyze_balance(routine: dict) -> dict:
    """
    ALWAYS call after generating a routine, before presenting it.
    Performs arithmetic and rule-checking the model should not do itself.
    """
    days = routine.get("days", [])
    minutes_per_day, all_themes = [], []

    for day in days:
        activities = day.get("activities", [])
        minutes_per_day.append(sum(a.get("duration_min", 0) for a in activities))
        all_themes.extend(a.get("theme", "unknown") for a in activities)

    total_minutes = sum(minutes_per_day)
    theme_counts = {t: all_themes.count(t) for t in set(all_themes)}
    diversity_score = round(len(set(all_themes)) / len(all_themes), 2) if all_themes else 0.0

    warnings = []
    for i in range(len(days) - 1):            # Rule: consecutive same-dominant-theme days
        if dominant_theme(days[i]) == dominant_theme(days[i+1]):
            warnings.append(f"Day {i+1} and Day {i+2} share dominant theme")
    for i, total in enumerate(minutes_per_day): # Rule: day exceeds 90 min
        if total > 90:
            warnings.append(f"Day {i+1} exceeds 90 minutes ({total} min)")
    if diversity_score < 0.4:                  # Rule: low diversity
        warnings.append(f"Low diversity score: {diversity_score} (target ≥ 0.4)")

    return {                                   # ← typed return, not free text
        "total_minutes": total_minutes,        # int
        "minutes_per_day": minutes_per_day,    # list[int]
        "theme_counts": theme_counts,          # dict[str, int]
        "theme_diversity_score": diversity_score, # float 0.0–1.0
        "warnings": warnings,                  # list[str]  ← not "looks repetitive"
    }

Demo recap

What you just watched — and what to look for in your own build.

What worked

  • analyze_balance called before final response
  • Warnings acknowledged, fix offered
  • 30-day request refused cleanly
  • Alternatives pulled from catalog

Things to notice in traces

  • How many model calls per routine?
  • Did analyze_balance run post-generation?
  • What did propose_alternatives receive?
  • Where did the callback fire?

Common failure modes

  • Tool not called → fix the docstring
  • Wrong args passed → check Args section
  • Spec not enforced → make INSTRUCTION more explicit
  • LLM inside a tool → refactor to pure Python
