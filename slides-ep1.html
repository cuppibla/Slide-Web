Slide 5 — Subscriber vs Callable comparison · Scene 6 (~6:30)
Dispatch Modes

Two ways agents receive work

Subscriber
  • Long-lived Redis pub/sub subscription
  • Wakes on every simulation tick
  • Sub-millisecond — no HTTP latency
  • For the runners — 1,000s at once
  • Always at least one hot instance
The "doers" — the hot path
Callable
  • Standard A2A over HTTP
  • Invoked on demand
  • Scales to zero — no idle CPU cost
  • For the planner & simulator
  • Runs on Agent Runtime
The "thinkers" — occasional work

Slide 6 — War story before/after · Scene 7, the HTTP→Redis story (~9:00)
A Scaling Decision

Why we threw out HTTP

Tried
HTTP A2A
The default way A2A agents talk — start with the standard.
→
Problem
The network is the bottleneck
1,000 sessions need responses in <10s. HTTP overhead per call won't scale.
→
Solution
Redis pub/sub
Memory Store — one broadcast reaches every agent. 100,000+ messages/node.
Target: respond to 1,000 agents in under 10 seconds  ·  sub-millisecond fan-out
